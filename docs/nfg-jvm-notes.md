# NFG on the JVM backend — scoping notes

Starting point for implementing Raku's Normalization Form Grapheme on the JVM
backend. Nothing here is implemented yet; this is the survey that a first
attempt should start from.

## What the gap actually is

MoarVM strings are NFG: a string is a sequence of *graphemes*, and every string
op counts and indexes in graphemes. JVM strings are `java.lang.String`, so they
count and index in UTF-16 code units, and no normalization happens at all.

Measured, `nqp-m` versus `nqp-j` today:

| input | op | MoarVM | JVM |
| --- | --- | ---: | ---: |
| `"a" + U+0301 + "b"` | `nqp::chars` | 2 | 3 |
| `"á" + "b"` (precomposed) | `nqp::chars` | 2 | 2 |
| `"x" + CRLF + "y"` | `nqp::chars` | 3 | 4 |
| `U+1F469 ZWJ U+1F4BB` | `nqp::chars` | 1 | 5 |
| `"a" + U+0301` vs `"á"` | `nqp::iseq_s` | 1 | 0 |
| `"a" + U+0301 + "b"` | `nqp::index(…,"b")` | 1 | 2 |
| `"a" + U+0301 + "b"` | `nqp::eqat(…,"b",1)` | 1 | 0 |

So this is not a corner of the string ops, it is the whole indexing model,
plus string equality. It predates and is independent of the ignorecase and
ignoremark work — those ops inherit the gap rather than adding to it.

## The encouraging part

The JDK already agrees with MoarVM on where the grapheme boundaries are.
`java.text.BreakIterator.getCharacterInstance()` returns the same counts as
MoarVM's NFG for every case in the table above, including the two that are
easy to get wrong: CRLF is one grapheme, and a ZWJ emoji sequence is one
grapheme. `java.text.Normalizer.normalize(s, NFC)` handles the equality case
(decomposed NFC-equals precomposed).

That means a first implementation does not need MoarVM's synthetic-grapheme
machinery to get the observable behaviour right for ordinary text.

## How MoarVM does it, for reference

`MoarVM/src/strings/nfg.{c,h}`, ~600 lines, plus `normalize.{c,h}`:

- A string is an array of `MVMGrapheme32` (int32). Non-negative values are
  ordinary NFC codepoints.
- **Negative values are synthetics**: `-S - 1` indexes a table of
  `MVMNFGSynthetic`, which holds the base grapheme, the full codepoint
  sequence, and lazily cached uc/lc/tc/fc transforms.
- A trie maps codepoint sequences to graphemes, so the same cluster always
  gets the same synthetic.
- Reads are lock-free; adding a synthetic takes a mutex and copies rather than
  mutating, with frees deferred to a safe point.

The synthetic scheme exists so that a grapheme is always *one* integer, which
is what makes indexing O(1). Any JVM design has to decide whether it wants
that property.

## Three ways to do it here, roughly in order of cost

1. **Grapheme-aware layer over `java.lang.String`.** Keep the representation,
   NFC-normalize on construction, and make the ops that take or return
   positions translate through grapheme boundaries computed by
   `BreakIterator`. Cheapest, and no ABI change: `Ops.kt` signatures and the
   `Ljava/lang/String;` descriptors that `QAST/Compiler.nqp` bakes into
   generated bytecode all stay as they are. Cost is that every indexed op
   becomes O(n) in the string length unless boundaries are cached, so a
   boundary cache keyed on the string identity is probably needed early.

2. **NFG string type with synthetics in the Private Use Area.** Keep
   `java.lang.String`, but map non-composable clusters onto PUA code points so
   one grapheme is one `char` again and indexing goes back to O(1). The BMP
   PUA has 6400 slots and planes 15 and 16 add ~131k, which is finite; MoarVM's
   table is not. Also breaks any code that round-trips strings through the
   outside world without unmapping first.

3. **A real NFG string type.** An int-array representation mirroring
   MoarVM's, threaded through the runtime. Correct and O(1), but it changes
   the type of every string in the JVM backend, including the descriptors
   compiled into generated code and `stage0`, so it is a very large change.

Option 1 is the sensible first attempt: it is testable against MoarVM
immediately and it can be replaced underneath later.

## Where the work would land

- `nqp/src/vm/jvm/runtime/org/raku/nqp/runtime/Ops.kt` — the string ops.
  `chars`, `substr`, `index`/`indexfrom`, `rindex`, `eqat` and the folding
  family already added (`indexic`, `indexim`, `indexicim`, `eqatic`, `eqatim`,
  `eqaticim`), `ord`, `ordat`, `ordbaseat` (currently NYI, and Rakudo's
  INTERPOLATE.rakumod used to lean on it), `iseq_s`/`isne_s`/`cmp_s` for the
  normalization half, `codes`, `getcp`.
- Decoding paths in `io/` and `Buffers.kt`, if normalization happens on
  construction rather than lazily.
- `nqp/t/jvm/` for tests, and the `t/moar/*.t` string tests are reusable
  verbatim the way `07-eqatic.t`, `08-indexic.t` and `10-eqatim.t` already are
  as `t/jvm/13`, `12` and `14`.

## Suggested first steps

1. Write a cross-backend conformance test first: a corpus (decomposed,
   precomposed, CRLF, ZWJ emoji, astral, Hangul jamo) run through
   `chars`/`index`/`eqat`/`substr`/`ord`/`iseq_s`, with the expected values
   taken from `nqp-m`. It will fail on `nqp-j` at the start, and it is the
   thing that says when this is done.
2. Implement `chars` and `substr` over `BreakIterator` with a boundary cache,
   and see what the suite says.
3. Then the positional ops, then normalization-on-construction for equality.

## Gotchas already known

- `BreakIterator` instances are not thread-safe; one per use or a
  `ThreadLocal`.
- Rakudo's `Str.ends-with` computes its position as
  `chars(self) - chars(needle)`, which is already wrong for expanding folds on
  *both* backends. Do not treat that disagreement as an NFG bug.
- `nqp::chars` is extremely hot. Any implementation that walks the string on
  every call will show up immediately in build times — the setting compile is
  the benchmark that matters.
