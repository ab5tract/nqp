# Kotlin migration prototype — findings

Branch `kotlin-prototype`. Prototype scope: a representative slice of the
JVM runtime converted from Java to Kotlin under mixed compilation, with
full bootstrap + test-suite verification after each step. This document is
the go/no-go input for any full migration, and for the later
`org.raku.rakudo` layer (rakudo's `src/vm/jvm/runtime`, 6 files/3,094 lines).

## What was converted

| Slice | Files | Notes |
|---|---|---|
| `runtime/Base64`, `runtime/Buffers` | 2 | static-utility classes → `object` + `@JvmStatic`; exercised by every bootstrap stage (SC serialization) |
| `runtime/HLLConfig` | 1 | all-public-mutable-field config record → 45 × `@JvmField var ...: T? = null` |
| `io/IIO*` interfaces | 14 | mechanical; Java implementors unchanged |
| `io/FileHandle`, `io/StandardReadHandle` | 2 | subclass of Java `SyncHandle` (protected-field access), jline, NIO |
| `sixmodel/reprs/VMArrayInstance_i` | 1 | monomorphized array REPR instance; `@JvmField` hot fields |

Totals: **20 files, 1,105 Java lines → 988 Kotlin lines** (−11% on a
deliberately literal port), 48 `@JvmField` + 5 `@JvmStatic`.

Verification: full Gradle bootstrap (stage1+stage2) plus `prove t/nqp`
after slice 1 — **identical to baseline**: 110 files, 9,121 tests, same two
pre-existing upstream failures (`019-file-ops.t` plans 112/runs 98,
`116-streaming-decoder.t` BufferOverflowException at 30/70; both fail
identically on the pure-Java Makefile build). Slice 2 verified against
t/nqp + t/hll + t/qregex + t/qast + t/serialization: 122 files,
11,969 tests, again only those same two failures.

## Friction inventory

1. **`@JvmField`/`@JvmStatic` churn is real but shallow.** Every raw public
   field needs `@JvmField` to keep the class-file shape (getfield/putfield
   from Java neighbors, rakudo's Java layer, and — for the core classes —
   generated bytecode). HLLConfig alone needed 45. It is mechanical and
   grep-auditable (`grep -L JvmField` on converted files with public vars).

2. **Nullability is the substantive design question.** Faithful ports force
   `T?` everywhere Java allowed null (HLLConfig fields, `slots: LongArray?`),
   which then costs `!!` at use sites (VMArrayInstance_i has ~15). The Java
   code's implicit invariants ("slots is non-null once elems > 0") don't
   translate for free. A non-literal port could encode them properly, but
   that changes behavior on edge paths (KotlinNPE vs NPE location) and must
   not be done during a parity-focused migration.

3. **Name collisions field-vs-method.** NQP's style pairs a public field
   `elems` with a method `elems(tc)`, or a field `lock` with a method
   `lock(tc, flag)`. Kotlin tolerates property/function namespace splits,
   but `FileHandle.lock` (a `FileLock`) had to be renamed (`fileLock`,
   private — safe here, but it would be an ABI break on a public field).

4. **Package-private and protected Java members work.** Kotlin code in the
   same package/module accesses Java package-private and protected members
   (`SyncHandle.chan/readBuffer/eof/flushWriteBuffer`) without friction.
   `super.clone()` against `Cloneable` Java superclasses also works.

5. **Behavior-preserving means bug-preserving.** `Base64.decode` constructs
   `RuntimeException`s it never throws (missing `throw` upstream) —
   the port keeps the do-nothing behavior. A migration must resist the
   temptation to fix such things in the same commit.

6. **Runtime footprint.** kotlin-stdlib (+ `org.jetbrains:annotations`)
   joins the runner bootclasspath, jvmconfig jar list and install set
   (~1.6 MB). `nqp-runtime.jar` grew 1,000,852 → 1,029,817 bytes (+2.9%)
   from Kotlin metadata annotations and `object` INSTANCE scaffolding.

7. **Kotlin/Gradle versions.** Kotlin 2.4.10 with `jvmTarget = JVM_9`
   matches `javac --release 9` (major 53). Gradle 8.14 requires a
   Java ≤ 24 JVM to run (pinned to 21 in gradle.properties); the Kotlin
   plugin warns that Kotlin 2.4 deprecates Gradle < 9 support — a Gradle 9
   upgrade should precede any large-scale conversion.

## Keep-as-Java list (do not convert without a dedicated effort)

- `runtime/Ops.java` — 707 static methods; the generated-code ABI. A Kotlin
  `object` would need `@JvmStatic` on every method; any signature drift
  breaks `QAST/Compiler.nqp`'s hardcoded descriptors and the stage0 jars.
- `runtime/IndyBootstrap.java` — invokedynamic bootstraps + MutableCallSite
  inline caches; names are baked into emitted `invokedynamic` instructions.
- `runtime/CodeRef`, `runtime/ResumeStatus`, `runtime/SaveStackException` —
  continuation protocol co-designed with the code generator.
- `runtime/CompilationUnit.java` — reflective `@CodeRefAnnotation` scan;
  superclass of every generated class.
- `jast2bc/AutosplitMethodWriter.java` — ASM tree surgery.
- `sixmodel/reprs/P6OpaqueBaseInstance.java` — `sun.misc.Unsafe` CAS on
  reflective field offsets. Port to `VarHandle` **in Java first** (the code
  comment already suggests it), independent of any Kotlin work.
- `sixmodel/REPRRegistry.java` — order-sensitive static initializer; REPR
  ids are serialization indices.

## On the VMArrayInstance duplication

The ~21 `VMArrayInstance_*`/`MultiDimArrayInstance_*` monomorphizations
(~5k lines) port 1:1 (this prototype's `_i` variant is representative; the
`_s`/`_n`/sized-int variants differ only in slot type and the handful of
widening/boxing sites). Kotlin generics cannot collapse them without
boxing — reified generics don't exist on the JVM and primitive
specialization is exactly what these classes hand-implement. The realistic
dedup options are (a) a small Kotlin/Gradle code generator emitting the
variants from one template (fits naturally in buildSrc), or (b) leaving
them: they are stable, closed code. Recommendation: (a) only if a full
migration proceeds, as its pilot for generated sources.

## Recommendation

Mixed Java/Kotlin compilation is production-ready for this codebase: the
converted slice bootstrapped the compiler and matched the test baseline
exactly on the first attempt. An incremental, ABI-preserving migration is
**feasible** with this recipe per class:

1. `grep` the class name in `QAST/Compiler.nqp`; if present → keep-as-Java
   list (or plan a lockstep descriptor update).
2. Convert literally; `@JvmField` every public field, `@JvmStatic` every
   static; do not "fix" anything.
3. `./gradlew buildJvm testNqpCore` and require exact baseline parity.

Sensible order: finish `io/`, then small `runtime/` value classes, then
`sixmodel/reprs/` leaves, then `sixmodel/` core — reassessing after each
package whether the (modest) readability gain keeps justifying the churn.
The `org.raku.rakudo` layer should wait until NQP's runtime conversion has
settled, since all six files depend on `org.raku.nqp` types; its own
hazards (`RakudoContainerSpec`'s Unsafe use, `Binder`'s hot paths,
`RakudoJavaInterop`'s MethodHandles) mirror the keep-as-Java list above.
